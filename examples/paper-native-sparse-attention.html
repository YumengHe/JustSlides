Training and prefill  ·  Compute-bound

●All tokens are processed together in large matrix multiplies

●Attention compute grows as O(n²), so speeding up means doing fewer FLOPs

Decoding  ·  Memory-bound

●Only one new token per step, yet the whole KV cache is read every step

●Speeding up means reading fewer keys and values

A useful sparse method has to cut both FLOPs in prefill and bytes read in decoding

KV cache = 30 layers × 4 KV heads × (192 + 128) numbers × 2 bytes ≈ 77 KB per token, our estimate from the configuration in Section 4.1.

Multi-head  Each head keeps its own keys and values, so the KV cache is the largest

Grouped-query  NSA builds on GQA. Methods that pick KV blocks per head, like Quest, make a group load the union of its heads' blocks, so memory traffic barely drops

Multi-query  One K/V head for all query heads gives the smallest cache, but can hurt quality

Full  Every query scores every earlier key, so cost grows as O(n²) with context length

Window  Cheap, but anything outside the window is invisible, so long-range dependencies are lost

Global  The pattern is fixed in advance and cannot adapt to what each query needs

Dynamic  Existing methods are sparse in only one phase (MInference in prefill, H2O in decoding), and they are added after training, so pruning loses information the dense model relied on

NSA keeps dynamic sparsity, but makes it work in every phase, align with GQA and GPUs, and train from scratch

Each branch has its own key/value projections. Each gate is a score in [0, 1] from an MLP with a sigmoid.

three branches, combined by a gate

Scores cluster in blocks (schematic of the paper's Fig. 8)

Why blocks?  Attention scores cluster in blocks, so compression and selection can score whole blocks with little loss, and GPUs read a block stored side by side far faster than scattered tokens. The sliding window is one unbroken stretch already.

Discussion: Is NSA Used in Production?

DeepSeek: from blocks to tokens

V3.2 (2025) switched to DeepSeek Sparse Attention, where a small indexer picks individual tokens. V4 (2026) adds KV compression on top, and GLM-5 also uses DSA.

OpenAI gpt-oss: a fixed pattern

Alternates dense layers with 128-token sliding-window layers, a simple fixed pattern rather than learned sparsity.

Follow-up research

FSA speeds up the kernel for small GQA groups. InfLLM-v2 removes the extra parameters. MoBA, released the same week, selects blocks with a single branch.

Remaining weaknesses

Needs many query heads per GQA group (16 in the paper). Three branches add parameters and tuning. All results come from one 27B model.

NSA itself is not deployed as published, but its core idea, trained and hardware-aware dynamic sparsity, lives on

Sources: DeepSeek-V3.2-Exp and V4 technical reports, OpenAI gpt-oss model card, FSA (arXiv 2508.18224), InfLLM-v2 (ICLR 2026), MoBA (Moonshot AI, 2025).

Short contexts  Dense attention with GQA is still hard to beat, with simple and mature kernels

Long contexts  Skipping most keys, through sparsity or linear layers, becomes necessary

Hardware  Algorithms must be co-designed with GPU kernels to give real speedups, NSA's main lesson

Training  Sparsity works best when the model learns it, not when it is added afterwards
